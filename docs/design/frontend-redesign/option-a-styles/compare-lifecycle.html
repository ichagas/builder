Building vs. after release: three approaches

Blueprint style. Pronghorn covers building the app and then changing it (bug fixes, enhancements, features). It does not monitor the running app. Each approach shows the same project before its first release (left) and after it (right). Every frame is live. See LIFECYCLE.md for the reasoning.

APPROACH 1

Baseline + work items

Open

One navigation for the project's whole life. After the first release, a Work list and a Working on switcher appear above the same four phases, and the phases re-scope to one work item. The difference between building and after release is small and gradual. Only the "after release" side is prototyped. Before release it would look like the original Option A, without Work or the switcher.

APPROACH 2

Build mode → Evolve mode

Open

Two clearly different modes with an explicit first release step between them. In Build mode the rail is the four phases and the agent commits to main. In Evolve mode the rail becomes Changes, Releases and a locked Baseline (requirements, architecture, code, data). The four phases move inside each change as a stepper. The top bar's color band and badge show the mode everywhere.

APPROACH 3

Version timeline

Open

The unit of work is a version. A timeline strip is always visible. Everything left of the First release flag is the build era, and everything right of it is changes. Before the first release there is one version, v1.0.0. After it, each request is scheduled into a hotfix or the next version, and selecting a version scopes the four phases to it. Released versions are read-only. Versions go out in order, and unfinished changes move forward automatically.
